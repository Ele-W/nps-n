# NPS V2 改动路线与交付清单（建议稿）

配套架构：[2026-11-24-nps-v2-design.md](2026-11-24-nps-v2-design.md)。此文件是评审用路线，不代表代码实施已启动，也不是工期承诺。

配套原型：[离线网页、截图与中文维护说明](../../design/nps-v2/README.md)。可直接下载原型目录打开 `index.html` 评审，无需启动现有 Go 项目。

## 推荐方向

保留 Go 穿透核心；先重建独立身份、设备与配置模型，再做 Web 与桌面产品。框架选择服从启动/内存实测，不用全量 Rust 重写换取未经测量的收益。初期模块化单体、单节点，不预先建设微服务或集群。

## P0：确定基线，先做最小可用闭环的设计与验证

涉及：当前工作区、`go.mod`、`cmd/nps`、`cmd/npc`、`gui/npc`、`server`、`bridge`、`client`。

交付物：

1. 现有未提交修改清单及保护方式，尤其是认证/CSRF/桥接安全修改与测试。
2. 当前支持协议、认证与配置行为清单，包括不能丢失的高级选项。
3. 旧 npc / 新服务端、旧服务端 / 新 Agent、新旧配置文件的兼容矩阵。
4. 固定 Win/macOS 参考机；相同功能的 Fyne/无 WebView 候选与 Wails 性能对比。
5. 本次交互原型评审记录：信息结构、术语、新建流程、异常处理、账户切换。

出口：用户确认桌面预算、首版是否要求未登录运行、管理员访问边界；选定桌面壳。完成基线才改变网络行为。

## P1：把账户、设备和权限建立在数据层

涉及：新增 `internal/domain`、`auth`、`repository`、`application`、`api/v2`；旧 `lib/file` 只保留兼容适配，不继续扩充用户模型。

建议工作包：

- 设计数据库 schema 和迁移版本，明确所有者约束、唯一公开端点、撤销与审计字段。
- 建立用户登录、浏览器会话、桌面授权、设备登记/轮换/撤销。
- 建立用户范围的仓储接口，业务层没有无范围的用户资源读取方法。
- 编写 `/api/v2` OpenAPI：认证、设备、隧道、配置版本、状态、诊断、用量和管理接口。
- 建立端口池、域名命名空间、自定义域名控制权验证。
- 管理员管理账户状态和配额，与普通用户资源读取权限分开。

出口：使用真实数据库与两个账户进行 API 交叉测试；资源 ID 替换、批量、导出、日志、SSE 均无法越权；归属错误的创建没有副作用。

## P2：把新管理层接到现有转发核心

涉及：新增 `internal/engine`、`reconcile`；适配 `server/server.go`、`bridge/bridge.go`、`server/proxy`、`client`。

建议工作包：

- 定义 Engine 启停设备/隧道、读取快照、订阅事件的窄接口。
- 建立配置版本、ETag/409、事务 outbox、幂等应用和回执状态机。
- 明确公开端点“预留→切换→确认→释放”的故障恢复步骤。
- 用户停用、设备撤销和配额变更能作用于已有连接。
- 保留旧协议适配，但标识旧客户端不支持的确认能力。
- 新配置写入只走新用例服务；旧 Web 在切换后停写，避免双写漂移。

出口：TCP 与 HTTP 端到端闭环先通过；重复请求、离线、进程崩溃恢复、旧回执和冲突均有确定行为；再完成 UDP/HTTPS/SOCKS5/P2P 等现有能力回归。

## P3：重写 Web 用户控制台

涉及：新增 `apps/web`、`packages/api-client`、`packages/design-tokens`；逐步替换 `web/views`/静态 jQuery 页面。

建议页面顺序：

1. 登录与首次使用：进入个人空间 → 接入设备。
2. 设备：在线/离线、版本、登记、撤销及关联隧道。
3. 隧道：列表 → 场景向导 → 详情 → 配置状态/回退。
4. 故障处理：原因、检测、日志、重试；不只弹出“操作失败”。
5. 用量与活动：本账户配额、流量、关键操作。
6. 账户安全与独立管理员入口。

交互要求：局部更新保留用户上下文；表单输入不丢；错误就地解释；保存/生效分开；复制按钮有反馈；搜索与筛选可清空；全部核心操作可用键盘完成。移动宽度重排，不把桌面界面整体缩小。

出口：新用户能完成首次接入到可访问隧道；设备离线、目标服务未启动、端口占用、域名未验证、额度不足与版本冲突都有可继续操作的路径。

## P4：交付 Win/macOS 桌面客户端

涉及：新增 `cmd/nps-agent`、`internal/agent`、`localipc`、`apps/desktop`；复用 `client` 核心；旧 `gui/npc` 在新产品稳定后退役。

建议工作包：

- 提取 Agent 生命周期，不以窗口是否存在决定隧道是否运行。
- 实现 OS 用户级自动启动与受保护 IPC；本机 UI 授权与设备后台凭据分开。
- 系统浏览器登录/设备登记、首次连接、保存本地快照。
- 连接概览、常用隧道、新建、复制、暂停、诊断、日志和偏好。
- 普通注销/解除设备/退出窗口/停止后台的文案与行为保持一致。
- 单 Agent 绑定单账户；账户不一致时不加载旧账户资源，提供明确的重新认证解除/本地重置路径。
- 托盘与窗口资源释放；休眠唤醒、网络切换、重连和更新恢复。
- Windows 与 macOS 分别构建、签名、安装、卸载和更新验证。

出口：在真实 Release 安装包上通过性能关卡；窗口关闭后没有残留 WebView，隧道不中断；所有相关进程总物理内存纳入测量。若壳未达标，先换/减 UI，不直接重写网络核心。

## P5：迁移、灰度与稳定发布

涉及：新增 `internal/migration`、CI 发布流程、运维文档；保留旧二进制和数据备份。

建议工作包：

- `--dry-run` 检查旧带分隔符记录格式、重复用户名/密钥、孤立隧道和端点冲突。
- 生成旧身份到新账户/设备的映射报告；歧义记录不自动合并或激活。
- 独立数据库导入、密码哈希、未认领设备隔离、自定义域名认领。
- 维护窗口停止旧写入/旧进程，最终迁移并核对归属与数量。
- 小范围真实用户验证，确认所有保留协议与配置语义。
- 演练备份恢复和回退；明确 V2 上线后增量不会自动回灌旧文件。
- 文档化安装、登记、配置、异常处理、日志位置、升级与恢复。

出口：成功演练实际数据迁移与回退后再扩大发布。旧服务与新服务不同时占用相同公开入口。

## 开发顺序与用户操作流程

开发依赖：`P0 → P1 → P2 → P3/P4 联调 → P5`。桌面壳的性能探索在 P0 完成；接口稳定后两端可以独立开发，不提前复制两份业务规则。

用户首次使用：`登录 → 登记设备 → 选择用途 → 填本地地址 → 选择公开入口 → 校验 → 保存 → 等待回执 → 复制地址`。

故障处理：`发现异常 → 查看具体原因 → 运行检测 → 修改/恢复设备 → 重试 → 确认最新版本已应用`。

配置变更：`编辑 → 校验与影响提示 → 版本冲突检查 → 保存新版本 → 应用回执 → 成功或保留失败原因 → 必要时回退为新版本`。

## 首版范围取舍

必须有：账户隔离、多个设备、常用协议、新建向导、实际状态、设备撤销、诊断、迁移工具、Win/macOS 安装包。

后续再做：团队共享、计费、插件市场、多节点调度、复杂监控大屏、跨账户后台并行。现有高级协议不能直接删掉，可在新界面覆盖前保留明确标记的兼容路径。

## 进入代码实施前的产物

架构/UI 确认后，再编写按具体文件、接口、测试命令和提交边界拆分的实施计划。本路线不预造未来测试路径、不虚报通过，也不在设计阶段改写当前核心代码。
